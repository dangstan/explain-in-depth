# General explanation production plan

## Objective and completion

Create an accurate, useful explanation for all five mandatory audience purposes using traceable sources and an appropriate medium. Acceptance requires source fidelity, suitable instructional design and observed artifact behavior. Actual audience learning and presentation timing are separate evidence categories.

Finish when the finite generated task ledger and final review are accepted, every in-scope subject has accepted D1-D4 explanations and a D5 detailed map, required deliverables are accessible, preserved sources are checked and the closure report states remaining limits. Do not keep generating additional subjects or polish tasks.

## Phase one Establish the application

ITEM G5-01 resolves [INTAKE.md](INTAKE.md). Inventory supplied sources, existing explanations and reader needs. Distinguish facts, observations, interpretations, design intentions and illustrative examples. Identify material source conflicts before drafting the story.

Deliver intake, source and preservation inventories, an initial claim ledger and execution state. Missing nonessential evidence narrows a claim; a missing fact that determines the central explanation blocks only the dependent work.

## Phase two Design learning and bounded work

ITEM G5-02 designs all five mandatory depths, selects the medium and chooses a representative pilot subject. Build a subject brief with a consistent case, audience questions, essential concepts, likely misconceptions and discriminating acceptance questions.

Generate exact output destinations and concrete production cards from TASKS.md. Resolve every dependency and optional deliverable now. Each card owns a small reviewable outcome and named paths or document sections. Split large outcomes into stable suffixed IDs before dispatch, with corresponding graph updates.

Deliver populated subject briefs, an output manifest, route map, finite task graph and acceptance matrix. Review these as instructional design, not as proof of learner comprehension.

## Phase three Prepare the medium

ITEM G5-03 establishes only the necessary shared structure: document styles, slide conventions, website navigation, diagram notation, accessibility support or other selected scaffolding. A prose document does not need a JavaScript framework; an interactive visualization does need functional and fallback checks.

Deliver a representative rendered specimen, format-specific check method and preservation check. The specimen is a scaffold, not an accepted lesson. No standalone infrastructure project is implied.

## Phase four Produce and review the pilot

The pilot's mandatory D5 card creates or validates the detailed visualization or map and connects its material claims to precise sources. Its mandatory D1-D4 cards develop each audience explanation separately. INTEGRATE verifies direct entry, continuity, terminology, source links and transitions. Optional COMPANION cards create explicitly requested talks, exercises or summaries for a named audience.

Each card produces a frozen candidate, scoped checks and a separate reviewer verdict. ITEM G5-PILOT then reviews the entire pilot across depths, using the acceptance matrix and an unfamiliar changed case.

## Phase five Apply the accepted design

After G5-PILOT acceptance, execute each remaining subject's generated cards in the bounded order. Reuse conventions and useful components, not domain claims or storyboards. Independently review every new explanation. A pilot is evidence for shared design choices, not automatic acceptance of other subjects.

If there is only one subject, this phase has no cards. If two subjects need different visual grammars, document that difference instead of forcing both into the pilot's shape.

## Phase six Integrate and close

ITEM G5-QA verifies the full selected scope, cross-subject entry routes, preservation, output rendering, source links and claim qualifications. Repairs return to the owning card and receive fresh review; affected dependent acceptance is revisited.

ITEM G5-CLOSE records final destinations, accepted candidates, meaningful outcomes and evidence limits. A separate reviewer accepts that report before the track is marked complete.

## Scale to the real task

For a small topic, one subject can produce five short sections in one document. For a repository, subjects can be bounded subsystems. For a broad curriculum, subjects can be modules, with a deliberately limited first release. G5-02 fixes the release boundary before implementation.

All five purposes may share a file. Paths are not task boundaries by themselves: name section ownership and use one writer to prevent collisions. Do not impose a node count or minimum interaction count.
